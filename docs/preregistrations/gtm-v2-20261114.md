# Preregistration `gtm-v2-20261114`

GTM lead-qualification eval v2: a world-state-graded replication of the v1 run.

- Registrant: Karan Kapur (repository owner)
- Written: 2026-11-14, before any v2 model call
- Machine-readable manifest: `docs/preregistrations/gtm-v2-20261114.manifest.json`
  (generated by `python3 scripts/prereg.py build`; this document and that
  manifest are what the run receipt binds)
- Status: registered when this file and the manifest are committed. The
  run may not start before that; the runner enforces it (section 9).

## 1. What this is, and what it is not

**This is not a held-out confirmatory study.** The v1 run - same public
synthetic dataset, same prompt, same model identifier - was completed and
its results were read before this document was written (`REPORT.md`,
v1 legacy grading). Nothing here can be presented as a prediction made
blind to the data. The thresholds in section 6 were chosen with the v1
numbers in view.

What v2 is: an **engineering replication**. It re-runs the v1 design
under a stricter grading path (world-state grading, section 4) with the
design, counts, metrics, comparisons and stopping rule fixed and
committed in advance, so that the reported numbers cannot be shaped
after seeing them. The value of registering is procedural: no changed
denominators, no dropped rows, no extra runs, no reinterpreted metrics.

## 2. Design (fixed)

| item | value |
|---|---|
| arms | `treatment`, `placebo`, `baseline` |
| model (treatment, placebo) | `claude-fable-5-2`, requested explicitly via `--model` |
| model runtime | local Claude Code CLI, `-p --output-format json`, tools disabled (`--tools ''`), `--no-session-persistence`, no extra flags, 180 s timeout, each call started from an empty scratch directory outside the repository |
| baseline | deterministic rules (`harness/runner.py: rules_baseline`), no model |
| dataset | `data/leads.jsonl`, 120 synthetic leads (seeded generator), sha256 `3b40af0733f0b768c04695d60726c295c7e536a320ea69aebd993b49e5b72277` |
| seed | `20261114` (fixes the placebo derangement) |
| runs per arm | 3 |
| lead-runs per arm | 120 leads x 3 runs = **360** |
| independent cases | **120** leads |
| model calls | treatment 360 + placebo 360 = **720** |
| total decisions | 3 arms x 360 = **1080** |
| trial plan sha256 (primary) | `e80e33f831fe865a4468980d41937e9b74110f690e45869290c1ecd4d69ae482` |

Arms:

- **treatment**: the qualification prompt on each lead's own signals.
- **placebo**: the same prompt, but each lead is shown another lead's
  signals (one fixed derangement from the seed; no lead keeps its own).
  The lead's identity and its truth label stay put.
- **baseline**: the deterministic rules qualifier on each lead's own
  signals.

The model sees only the rendered lead block inside the prompt. It runs
without tools and without session state, so it cannot read the truth
labels, the trial plan or the CRM database. The runner itself drops the
truth labels and the `tricky` flag before the first trial.

### Expected trial inventory

Exactly one trial per arm x run x lead: 3 arms x run indexes {0, 1, 2} x
lead ids `L0001`..`L0120`, with trial id `<arm>/r<run_index>/<lead_id>`.
That is 9 isolated CRM worlds of 120 leads each and 1080 trial
identities. The full list, including which lead's signals each placebo
trial is shown, is the trial plan; it is deterministic, its sha256 is
pinned above and in the manifest, and it can be written out with
`python3 scripts/prereg.py plan --slot primary --out <file>`. The
grader rejects a run whose inventory has any missing, duplicate, extra
or unknown trial or lead.

## 3. Hypotheses

Stated as expectations to be checked descriptively. v1's figures are
quoted from `REPORT.md` for context.

- **H1 - placebo control (validity gate).** With signals swapped, tier
  effect accuracy collapses towards chance while the treatment arm does
  not (v1: placebo 99/360, treatment 357/360). If this fails, the
  measurement is not responding to the leads and nothing else is claimed.
- **H2 - tier.** Treatment tier effect accuracy is near ceiling on this
  dataset and above the rules baseline (v1: 357/360 vs 321/360).
- **H3 - route.** Treatment route effect accuracy is not practically
  different from the rules baseline (v1: 321/360 vs 315/360, a 6
  lead-run difference).
- **H4 - delivery.** Every one of the 1080 planned decisions produces a
  consistent CRM effect; there are no unparseable answers, dropped
  dispatches or inconsistent effects (v1: 0 unparseable).

A note on what world-state grading can change: the simulator applies
accepted decisions faithfully, so if the harness is correct the effect
accuracy should equal the accuracy of the decisions themselves. v2 is
not expected to move the model's numbers because of the grading path.
It changes what counts as evidence, and it would expose a decision that
was claimed but never applied.

## 4. Outcomes and denominators

**Unit of evidence: the effect in the simulated CRM**, read offline from
the persisted world database - not the model's JSON, not its `reason`
text, not the runner's log.

Primary outcomes, per arm:

1. **Tier effect accuracy** = lead-runs whose CRM lead record carries
   the true tier, confirmed by a dispatch event whose receipt is valid
   and agrees with that state / **all 360 planned lead-runs**.
2. **Route effect accuracy** = lead-runs whose lead is a member of the
   true route's queue, confirmed the same way / **all 360 planned
   lead-runs**.

Failures are never excluded. An unparseable answer (recorded as a
rejection: the lead stays unqualified and unrouted), a dropped dispatch
(no event), or an inconsistent effect (state and receipt disagree) is
wrong for tier and for route and stays in the denominator. This differs
from v1 legacy grading, which counted unparseable rows separately.

Truth labels come from the dataset file, checked against the pinned
sha256. Labels or correctness flags appearing anywhere else are ignored.

Secondary outcomes (descriptive, no criteria attached):

- **Calibration.** The model's self-reported confidence against tier
  effect correctness: ECE (5 bins), Brier score, direction. The
  confidence is a self-report taken from the decisions log; it is the
  only reported quantity that rests on the log, and it is explicitly
  not effect evidence. Lead-runs with no reported confidence are counted
  and left out of calibration (they remain failures above).
- **Stability.** Per-lead flip rate of the tier assigned in the CRM
  across the 3 runs; per-run accuracy and its spread.
- Clean vs tricky gap; tier and route outcomes by true segment.

## 5. Planned comparisons

Repeated runs of one lead share its signals and label, so 360 lead-runs
are **not** 360 independent cases. Between-arm comparisons are therefore
**paired per lead**, n = 120:

- for each lead, d = (share of its 3 runs correct in arm A) - (share
  correct in arm B);
- reported: mean of d, number of leads with d > 0, d < 0, d = 0, and the
  raw lead-run delta.

Comparisons: treatment vs baseline, and treatment vs placebo, each for
tier effect and route effect. Lead-run totals are reported next to them
with their denominators.

**No significance test is planned and no p-value will be reported.**
This is a small, synthetic, hand-labeled dataset already seen once; the
run is descriptive. No claim that the model is superior (or inferior) to
the rules baseline will be made from it in an inferential sense.

## 6. Prespecified descriptive criteria

Evaluated mechanically by the grader with exact arithmetic on the
counts, on the primary run only. Each has a reading fixed in advance for
both outcomes (the exact text is in the manifest and is printed in the
report). Accuracies are lead-run effect accuracies over 360.

| id | met when | if not met |
|---|---|---|
| H1 | placebo tier accuracy <= 0.50 **and** treatment - placebo tier accuracy >= 0.25 | the measurement is declared invalid for this run; no treatment or baseline-delta claim is made |
| H2 | treatment tier accuracy >= 0.95 **and** treatment - baseline tier accuracy > 0 | reported as a non-replication of v1's tier result |
| H3 | abs(treatment - baseline route accuracy) <= 0.05 | reported as a non-replication of v1's routing finding, direction and size as observed, no superiority claim |
| H4 | undelivered decisions across all arms = 0 | failures are counted by kind; they already count against every accuracy |

These are thresholds for describing the result, not tests. Meeting or
missing one says how this run compares with v1 on this dataset, nothing
more general.

## 7. Stopping, failures, restarts

- The run **aborts on the first CLI failure** (signed out, timeout,
  nonzero exit, error envelope). **No retries**, at any level.
- An aborted attempt keeps its `.partial` directory and an
  `ABORTED.json`. It has no manifest, cannot be graded, is never pooled
  with anything, and is disclosed.
- **No optional stopping.** There is no interim look at outcomes. An
  attempt ends only by completing all 1080 planned decisions or by a CLI
  failure, which is an infrastructure event, not a judgment about
  results.
- **Restart rule.** After an aborted attempt, a fresh attempt may run
  the full plan from the start in a new attempt directory
  (`results/v2/gtm-v2-20261114/attempt-NN`). No resuming, no splicing.
  The **first complete attempt is the primary result** and the runner
  refuses any further attempt. Each receipt lists the earlier attempts
  found on disk.
- Unparseable model answers are not CLI failures: they are recorded and
  graded as failures (section 4), and the run continues.

## 8. Smoke run (separate, optional)

A health check that the CLI is reachable and answers parse:

- first 12 leads, 1 run, all three arms: 24 model calls, 36 decisions;
  trial plan sha256
  `99e1241050ac304bb985d15bb7f7deae857b6f48bd9b8f164dbffbd39658894a`;
- run with `--prereg ... --smoke`, under the same gates as the primary;
- completes at most once and only before any primary attempt (a smoke
  attempt aborted by a CLI failure may be repeated, and is disclosed);
- **its numbers are outside the primary counts and are never pooled.**
  Its 12 leads are also in the primary run; that overlap is disclosed
  here and in the smoke report;
- no pinned input may change between the smoke and the primary run. If
  the smoke exposes a defect that needs a code change, this
  preregistration is void for the changed code (section 10).

Mock-backend runs are harness tests. They involve no model and are never
part of any count.

## 9. Commit-before-run, and what is pinned

The machine manifest pins, by sha256: the dataset; every `harness/*.py`
file and the run/grade/report/prereg entry points (the source set); the
prompt template; the scorer (`harness/world_grade.py`, `harness/world.py`,
`harness/integrity.py`); the design configuration; and the primary and
smoke trial plans.

A file cannot contain its own hash, so **the manifest itself and
everything under `docs/` are outside the pinned set**. They are bound a
different way: before any model call the runner records, in the run
receipt, the git commit it verified at and the sha256 and git blob id of
the committed manifest and of this document.

`run_world_eval.py --prereg` (and `scripts/prereg.py verify`) refuse to
proceed, before any model call, unless:

1. the manifest regenerates byte-identically from the working tree -
   so the current dataset, source, prompt, scorer, configuration and
   plan hashes all match the registration;
2. the manifest, this document, the dataset and every pinned source
   file are committed at `HEAD` and byte-identical to the committed
   version;
3. there are no uncommitted changes to any of those files;
4. the command line carries no design overrides (model, runs, seed,
   arms, limit, dataset and extra CLI flags are fixed by the manifest).

The grader later requires the manifest named in the receipt, by sha256,
and checks that the run's dataset and plan are the registered ones.

## 10. Deviations

Any change to a pinned input after registration voids this
preregistration for that run. It needs a new preregistration id and
commit, and the report must say what changed and why. Results from a
voided registration may be reported only as exploratory.

## 11. Boundaries of these guarantees

- The CRM is a local simulator owned by the harness. It is not a
  production CRM and not an independent security boundary. The
  separation that means something is between the harness and the model
  under test.
- Hashes, receipts and read-only file modes are consistency checks.
  They catch accidents, partial runs and careless edits. Whoever
  controls the machine can rewrite the files and recompute every hash.
- A local git commit orders events only as far as it is published.
  Pushing the registration commit before the run is what gives the
  ordering an outside witness; the harness cannot check that.
- The harness records which model it requested and any model
  identifiers the CLI reports back. It cannot independently attest
  which model served a call.
- The dataset is synthetic, small and hand-labeled, and has been used
  before. Everything reported is about this prompt, this model
  identifier and this dataset.
